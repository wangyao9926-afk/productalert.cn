# PostgreSQL Migration Plan

当前代码仍以 SQLite 作为本地运行数据库。第 15 步开始做的是迁移准备：集中数据库配置入口，明确 PostgreSQL 切换前需要完成的 SQL、驱动和任务队列改造。

## 当前配置

默认不需要配置：

```powershell
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

默认数据库：

```text
data/monitor.db
```

可通过 `.env` 或环境变量指定 SQLite 文件：

```env
DATABASE_URL=sqlite:///data/monitor.db
```

如果配置 PostgreSQL：

```env
DATABASE_URL=postgresql://user:password@localhost:5432/product_monitor
```

当前版本会主动拒绝启动，并提示仍处于 migration-prep mode。这是故意的：代码里仍有 SQLite 专属 SQL，不能假装已经完成切库。

## PostgreSQL 切换前必须处理

1. SQL 占位符
   - SQLite: `?`
   - PostgreSQL/psycopg: `%s`

2. 自增主键
   - SQLite: `INTEGER PRIMARY KEY AUTOINCREMENT`
   - PostgreSQL: `BIGSERIAL PRIMARY KEY` 或 `GENERATED BY DEFAULT AS IDENTITY`

3. 忽略重复插入
   - SQLite: `INSERT OR IGNORE`
   - PostgreSQL: `INSERT ... ON CONFLICT DO NOTHING`

4. 最近插入 ID
   - SQLite: `cursor.lastrowid`
   - PostgreSQL: `RETURNING id`

5. SQLite PRAGMA
   - `PRAGMA foreign_keys`
   - `PRAGMA table_info`
   - `PRAGMA index_list`
   - PostgreSQL 需要换成 `information_schema` / `pg_catalog`

6. 时间默认值
   - SQLite: `CURRENT_TIMESTAMP`
   - PostgreSQL 可用 `CURRENT_TIMESTAMP`，但建议统一成 `TIMESTAMPTZ`

7. JSON 字段
   - 当前使用 `TEXT + json.dumps`
   - PostgreSQL 应迁到 `JSONB`

8. 并发和事务
   - PostgreSQL 支持多 worker 并发写
   - 任务领取、通知 outbox 处理需要行级锁，例如 `FOR UPDATE SKIP LOCKED`

## 已完成的适配准备

- `app.settings.database_settings()`：集中解析 `DATABASE_URL`。
- `app.db.insert_ignore()`：集中 SQLite `INSERT OR IGNORE` 语义。
- `app.db.last_insert_id()`：集中 SQLite `cursor.lastrowid` 语义。
- `app.db.table_columns()` / `app.db.index_columns()`：集中 SQLite `PRAGMA` 元数据读取入口。
- `app.db.assignment_list()`：集中动态 `SET field = ?` 片段生成，并校验字段名。
- `app.db.update_by_id()`：集中常见按 `id` 更新。
- `app.db.update_by_id_when()`：集中带状态条件的按 `id` 更新，用于任务领取。
- `app.db.select_by_id()`：集中常见按 `id` 查询。

## Step 18: Queue Claim Boundary

当前 SQLite 运行时已经先做 claim，再执行副作用：

- `scan_jobs`：只有 `queued` 任务可以被领取为 `running`。
- `notification_outbox`：只有到期的 `pending` 通知可以被领取为 `sending`，并在领取时递增 `attempts`。

这还不能替代分布式队列。目标是让业务代码先形成 PostgreSQL/Celery/RQ worker 需要的形态：先领取，再执行，最后持久化最终状态。

PostgreSQL 目标语义：

```sql
SELECT id
FROM scan_jobs
WHERE status = 'queued'
ORDER BY queued_at ASC, id ASC
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

也可以根据 worker 设计改为原子 `UPDATE ... WHERE status = 'queued' RETURNING *`。

## 仍需收拢的 SQLite 专属点

- 大量业务 SQL 仍使用 `?` 占位符。
- schema 仍使用 `AUTOINCREMENT`。
- migration 仍使用 `PRAGMA foreign_keys`、`PRAGMA index_list`。
- 复杂更新 SQL 仍需继续迁到 helper 或 query builder。
- PostgreSQL 版本需要用 migration 文件替代 `executescript`。

## 推荐下一阶段顺序

1. 新增数据库适配层，封装占位符、upsert、returning id。
2. 把 schema 拆出独立 migration 文件。
3. 加 PostgreSQL schema。
4. 用测试数据库跑 API 基础流程。
5. 再把任务队列切到 Redis/Celery 或 RQ。

## Step 20: SQLite Migration Files

The initial SQLite schema has been moved out of `app.db.init_db()` into:

```text
app/migrations/sqlite/001_initial_schema.sql
```

`init_db()` now loads `app/migrations/sqlite/*.sql` in filename order, then runs the existing compatibility migrations:

- `_migrate_existing_tables()`

- `_migrate_default_sources()`

This is still an idempotent bootstrap, not a full migration ledger. The next production-grade step is adding a `schema_migrations` table so each migration can be recorded, audited, and applied exactly once.

## Step 21: Migration Ledger

SQLite migrations now use a `schema_migrations` ledger:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version TEXT PRIMARY KEY,
    checksum TEXT NOT NULL,
    applied_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Behavior:

- Migration files are loaded from `app/migrations/sqlite/*.sql` in filename order.
- `version` is the SQL filename, for example `001_initial_schema.sql`.
- New migrations run once and are recorded with a SHA-256 checksum.
- Already-applied migrations are skipped when the checksum matches.
- Startup fails if a previously-applied migration file has a different checksum.

This gives us the production shape needed before adding PostgreSQL migrations: immutable migration files, an auditable ledger, and deterministic startup behavior.

## Step 22: PostgreSQL Target Schema

Added the first PostgreSQL target schema file:

```text
app/migrations/postgresql/001_initial_schema.sql
```

This file is not executed yet. `DATABASE_URL=postgresql://...` still fails fast in migration-prep mode.

Design differences from SQLite:

- `INTEGER PRIMARY KEY AUTOINCREMENT` becomes `BIGSERIAL PRIMARY KEY`.
- Time columns use `TIMESTAMPTZ`.
- Boolean flags use `BOOLEAN`.
- JSON text fields become `JSONB`.
- PostgreSQL JSON columns use semantic names such as `features`, `result`, `payload`, `metadata`, `diff`, and `notification_events` instead of SQLite compatibility names ending in `_json`.
- Queue/outbox indexes are ordered for claim queries: `status, queued_at/next_attempt_at ASC, id ASC`.

Before enabling PostgreSQL runtime, the DB adapter must map current application field names to the PostgreSQL column names or the application code must be migrated to semantic JSON names across both backends.

## Step 30: Backend-Aware Migration Service

Migration ledger logic now lives in:

```text

```

The new module owns:

- migration file discovery from the active backend;
- SHA-256 migration checksums;
- `schema_migrations` table creation;
- checksum mismatch protection;
- backend placeholder preparation for ledger queries;
- migration SQL execution.

`app.db` keeps compatibility wrappers such as `migration_files()` and `apply_sqlite_migrations()`, but the implementation delegates to `apply_migrations(db, DB_BACKEND)`.

This leaves `app.db` closer to a pure runtime database facade. Remaining PostgreSQL blockers are now more explicit:

- add a real PostgreSQL connection factory;
- replace SQLite `executescript()` semantics for PostgreSQL multi-statement migrations;
- define row mapping behavior for PostgreSQL cursors;
- keep SQLite maintenance gated to SQLite only when PostgreSQL runtime is enabled.

## Step 31: PostgreSQL Connection Factory

`app.db.get_db()` now selects a real connection factory from `DATABASE_URL`:

- SQLite keeps the existing `sqlite3` connection setup, row factory, and foreign-key PRAGMA.
- PostgreSQL uses `psycopg.connect(..., row_factory=dict_row)` and accepts `postgresql://`, `postgres://`, and `postgresql+psycopg://` URLs parsed by `app.settings`.
- Shared SQL helpers continue to prepare backend placeholders before execution.
- `insert_row()` uses `RETURNING id` on PostgreSQL instead of SQLite `lastrowid`.
- SQLite maintenance now runs only for the SQLite backend.

The PostgreSQL runtime path is no longer blocked by `require_sqlite()`. Remaining blockers are narrower:

- split or otherwise execute multi-statement PostgreSQL migrations without relying on SQLite `executescript()` behavior;
- finish validating application SQL against PostgreSQL semantics with a real database service;
- decide whether PostgreSQL runtime should use direct psycopg connections or a connection pool before production deployment.

## Step 32: Backend-Aware Migration Statement Execution

`app.db_migrations.execute_migration_sql()` no longer relies on SQLite `executescript()` behavior for every backend:

- SQLite migrations still use `executescript()` unchanged.
- PostgreSQL migrations are split into individual SQL statements and executed one by one through the active connection.
- The splitter handles semicolons inside single-quoted strings, double-quoted identifiers, line comments, block comments, and PostgreSQL dollar-quoted bodies.

This keeps migration execution intentionally small and local before introducing any heavier migration framework. Remaining PostgreSQL runtime work:

- validate the PostgreSQL schema file against a real PostgreSQL service;
- audit application queries for PostgreSQL-specific runtime behavior beyond placeholder translation;
- decide whether to add psycopg pooling before production use.

## Step 33: Offline Database Preflight

The preflight does not connect to SQLite or PostgreSQL. It validates the migration assets and backend configuration shape before runtime:

## Step 56: PostgreSQL + Redis Readiness Pass

Ran the real PostgreSQL + Redis deployment check against:

```text
DATABASE_URL=postgresql://product_monitor:change-me@localhost:5432/product_monitor
QUEUE_BACKEND=rq
REDIS_URL=redis://localhost:6379/0
```

The first PostgreSQL run exposed three production-only issues:

- boolean fields must receive Python booleans, not SQLite-style `0` / `1`;
- delete audit logs must be written before deleting the referenced site/source rows;
- PostgreSQL timestamp fields return `datetime` objects, while SQLite smoke data returns strings.

Fixes applied:

- site/source update endpoints now keep `enabled` as a boolean;
- site/source delete endpoints write audit logs before deletion;
- notification failure smoke accepts both `datetime` and ISO string timestamps;
- `deploy-check.ps1` now fails when the readiness subprocess exits non-zero.

Validated success output:

```text
ok database preflight duration_ms=...
ok database compatibility audit duration_ms=...
ok rq preflight duration_ms=...
ok rq queue smoke duration_ms=...
ok api smoke duration_ms=...
ok rq scan smoke duration_ms=...
ok notification outbox success duration_ms=...
ok notification outbox failure duration_ms=...
ok notification retry duration_ms=...
ok notification tenant isolation duration_ms=...
ok core tenant isolation duration_ms=...
production readiness smoke ok checks=11
Deploy check passed.
```

This fails before running smoke checks unless the active `DATABASE_URL` resolves to PostgreSQL. It prevents a deployment script from accidentally passing readiness checks against SQLite while the intended target is PostgreSQL.

Local SQLite validation can still be explicit:

```powershell
.\.venv\Scripts\python.exe -m app.production_readiness_smoke --require-backend sqlite
```

Mismatch output shape:

```text
RuntimeError: required database backend postgresql, got sqlite
```
