# 视觉证据包设计

## 目标

让每一条页面变化事件都能被运营人员复核：系统保存首次基线截图，并在文本或视觉发生变化时保存新的截图，在变化详情中安全地展示前后证据。

## 范围与非目标

本阶段只处理页面级截图证据、视觉变化比例和受鉴权保护的查看接口。它不包含第三方对象存储、区域化采集、OCR、图片标注层或长期保留策略；这些属于后续的生产规模化工作。

## 已选择的方案

采用“临时捕获、按变化持久化”的方案。

- 每次扫描在内存中通过现有 Playwright 渲染器获得 PNG 截图和 SHA-256 哈希。
- 首次基线必定持久化截图。
- 后续只有页面文本哈希变化或截图哈希变化时才持久化新的截图；无变化扫描只写轻量快照元数据，不写 PNG 文件。
- 截图写入后端私有目录 `data/evidence/`，绝不通过公开静态目录暴露。
- 本地磁盘是当前部署目标的持久卷；迁移到 S3/R2 时仅替换存储适配层，不改变快照和 API 契约。

不选择“每次扫描永久保存”，因为无变化页面会快速放大存储成本；不在本阶段接入对象存储，因为它增加云账号、密钥和运维边界，不能改善当前 P0 的抓取可证实性。

## 数据模型

给 `source_snapshots` 添加以下可空字段：

- `screenshot_hash`：当前临时截图的 SHA-256，用于判断视觉变化。
- `screenshot_path`：已持久化 PNG 相对 `data/evidence/` 的安全路径；无变化扫描为 `NULL`。
- `visual_change_ratio`：与最近一个已保存截图相比的像素变化比例，范围 `0.0` 到 `1.0`；基线为 `NULL`。
- `screenshot_error`：浏览器渲染或图片编码失败时的受控错误分类，不泄露堆栈或凭据。

截图文件路径由服务端根据 `source_id` 和 `snapshot_id` 生成，前端从不提交路径，也不从路径中推断授权。数据库迁移同时覆盖 SQLite 与 PostgreSQL，并保持旧快照可读。

## 采集和判定流程

1. 继续执行 HTTP 文本抓取与现有结构化抽取。
2. 使用受 SSRF 防护和请求路由保护的 Playwright 渲染器获取页面 PNG；渲染结果保留最终 URL、状态码和截图字节。
3. 将 PNG 标准化为 RGBA 后，用 Pillow 对齐尺寸并比较像素，得到变化比例；截图哈希也用于完全一致时的快速判断。
4. 找到同一监控源最近一个带截图的快照。首个截图为基线；后续在文本哈希变化、截图哈希变化或没有历史截图时写入 PNG。
5. 即使截图失败，文本快照、产品发现和事件链仍照常运行；快照记录受控错误原因，避免“截图服务故障”静默掩盖数据质量。

视觉变化比例用于解释和排序，不单独触发业务级新品、价格或库存事件；现有字段级事件仍是电商情报的主判断依据。

## 访问控制与 API

变化详情中的 `snapshot_before` 与 `snapshot_after` 在有截图时附带 `screenshot_url`。该 URL 指向受当前用户鉴权的 `GET /api/source-snapshots/{snapshot_id}/screenshot`：服务端通过快照、监控源和站点所有者联表校验权限，再以 `FileResponse` 返回 PNG。

未登录或非所有者访问返回 404；不存在、未保存截图或不在私有证据目录内的路径同样返回 404。截图路径不出现在前端公开资源目录中。

## 前端体验

变化详情用真实图片替换“变更前 / 变更后截图”占位块：有证据时展示图片与抓取方式、状态码、最终 URL；缺少前或后截图时显示准确原因，如“首次基线前无截图”“本次无视觉变化，未保存重复截图”或“截图渲染失败”。页面仍保留文本 Diff，二者共同支持人工判断。

## 测试与验收

测试必须在离线条件下覆盖：

- 首次截图写入私有证据目录并生成可读取的持久化字段。
- 完全相同的后续截图不会生成第二个 PNG。
- 文本或视觉变化会保存新的 PNG，并记录合理的变化比例。
- 截图渲染失败不阻断文本快照和扫描结果。
- 所有者可取得截图，其他用户与匿名用户无法取得。
- 前端类型、详情页图片和缺失证据提示通过构建与 UI 契约测试。

完成标准：用户创建监控后能在变化详情看到真实前后页面证据；不变化的扫描不持续累积 PNG；任意证据 URL 都不会越过站点所有权鉴权。
