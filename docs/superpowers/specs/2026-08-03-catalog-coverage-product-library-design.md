# 全量商品目录与产品库展示设计

## 目标

把“发现过链接”与“成功建立可信商品档案”明确区分。首次基线必须能覆盖一个公开独立站的可售商品目录；如果受限流、访问失败或解析失败影响而未达到可信程度，系统必须显示不完整状态，不能把少量结果宣称为完整基线。

同时将产品库从纯文本表格升级为可快速研判的商品档案列表：每个商品展示白底缩略图、名称、价格、库存、类型、卖点/功能摘要和原站链接。

## 问题与根因

Flextail 首扫中，系统发现了 172 个站内候选链接，其中包含大量 `/products/...` 商品 URL，但只建立了 9 条商品记录。对多个未入库商品页复测得到 HTTP 429。当前抓取器把读取失败折叠为 `None`，扫描循环仍将其计入“已处理”，最后仅以“已有至少一个商品”作为基线成功条件，导致结果错误显示为完整成功。

## 范围与非目标

本阶段覆盖：

- Shopify 商品 JSON、产品 Sitemap、集合页/分页和普通页面链接的组合发现与规范化去重。
- 公开站点的自适应礼貌抓取：按域名限速、识别 429 和 `Retry-After`、有限重试、暂停而非规避反爬措施。
- 扫描质量状态、失败分类、覆盖率统计，以及不可信基线的可恢复重试入口。
- 产品库的缩略图、卖点/功能字段、站点过滤与原站跳转展示。

本阶段不覆盖：代理池、绕过访问限制、登录后内容、站点私有 API、AI 自动补全商品数据、跨站同款匹配。

## 发现与抓取策略

### 商品来源优先级

1. 若公开 Shopify `products.json` 可用，分页读取最多 250 条/页的产品载荷，并直接由载荷生成商品候选与基础字段。
2. 读取根 Sitemap 和产品子 Sitemap；只把产品 Sitemap 中的商品 URL 作为商品候选，集合、博客、页面和 Sitemap 本身只作为发现辅助，不计入商品覆盖分母。
3. 对公开集合页和分页提取商品链接，补足没有 Sitemap 或 Shopify JSON 的站点。
4. 规范化 URL，并按 canonical 产品路径、平台产品 ID、SKU/GTIN（存在时）去重；同一商品的地区/语言 URL 选择站点默认语言或英文 URL 作为主记录。

### 访问限制处理

- 抓取层返回结构化读取结果，至少保留 HTTP 状态、最终 URL、错误类别和是否可重试，不能再用 `None` 吞掉失败。
- HTTP 429 归类为 `rate_limited`。读取 `Retry-After`；未提供时，使用有限指数退避和域名级冷却时间。
- 在冷却期间停止继续请求该域名，保留未处理产品队列；不通过代理、伪造身份或规避机制继续访问。
- 商品候选因 403、429、超时、非商品页、解析字段不足而未建立档案时分别计数。

## 基线质量门槛与状态

扫描任务需要分开保存：`discovered_product_count`、`attempted_product_count`、`stored_product_count`、`rate_limited_count`、`blocked_count`、`fetch_failed_count`、`non_product_count`、`parse_failed_count` 与 `pending_retry_count`。

- 只有没有未处理的可售商品候选、且没有限流/读取失败导致的未验证候选时，才可把站点标记为 `baseline_completed=true`。
- 已有部分商品但存在未验证候选时，任务状态为 `partial_success`，基线状态为 `incomplete`；产品库显示“当前已入库 N，待验证 M”，不把 N 标成官网总数。
- 全部候选无法读取时，任务状态为 `failed`，并显示最主要的失败分类。
- 用户可对 `incomplete` 基线发起“继续扫描”。该操作只恢复未验证候选，并在域名冷却时间结束后运行；已成功入库的商品不会重复生成新品事件。

## 产品库体验

### 列表信息架构

产品库按当前站点筛选。每行首列为 56×56 的白色图片容器：使用 `image_url` 的 `object-fit: contain` 图片；无图片或图片加载失败时显示产品名称首字母占位，不展示破图。

缩略图右侧显示：

- 商品标题与类型标签（标准商品、配件、套装、清仓等，来自 URL/标签/集合信号）。
- 1–2 条短卖点/功能标签，优先使用结构化产品标签和页面 feature/spec/benefit 信息；缺失时回退为描述的短摘要。
- 原站 URL 继续保留为外部新标签跳转。

价格、划线价、货币、库存、变体数、来源和最后验证时间保留在独立列。商品总数卡片的含义改为“已验证入库商品”；若基线不完整，同时明确展示“待验证商品”与质量告警。

### 结果入口

- 首扫页完成或部分完成后，显示已入库、待验证、受限流和失败数量，并提供“查看产品库”与“继续扫描”。
- 产品库页展示站点范围、基线状态与最后任务的质量摘要。
- 每条商品仍可进入本地详情页或打开原始商品页。

## 数据与接口边界

现有 `products` 继续保存 `image_url`、`features`、`description`、`item_type`、`url` 等字段。扫描任务的 `result.progress` 扩展质量计数，扫描结果携带可恢复候选的最小元数据。前端只依据 API 的质量字段显示状态，不从文字消息推断完整性。

新增或扩展的 API 契约：

- `GET /api/scan-jobs/{job_id}` 返回上述进度与质量统计。
- `POST /api/scan-jobs/{job_id}/resume` 仅允许站点所有者恢复 `incomplete` 或因可重试读取失败结束的任务。
- `GET /api/sites/{site_id}/baseline-summary` 返回已验证商品数、待验证数、基线状态、最新任务与主失败分类。
- `GET /api/products?site_id=` 保持返回图片、卖点、描述、类型和官方 URL。

## 测试与验收

- 单元测试：Shopify 载荷、产品 Sitemap、集合页候选被合并去重；非商品 Sitemap URL 不进入商品覆盖分母。
- 单元测试：429 与 `Retry-After` 会记录 `rate_limited`、停止继续拉取并使基线保持 `incomplete`。
- 单元测试：部分成功的首扫不生成新品事件；恢复后仅处理待验证商品，并不重复通知或重复入库。
- API 测试：任务质量统计和基线状态仅向所属用户暴露。
- UI 合约与构建测试：产品行包含图片容器、图片降级、类型及卖点字段；不完整基线显示质量告警与恢复操作。
- 真实站点验收：Flextail 不能再将 9 条商品误标为完整目录；遇限流时显示可解释的部分完成状态。公开 Shopify 数据可用时，应以其可获得的产品总数为基准；不可用时需显示覆盖受限，而不是声称全量。
